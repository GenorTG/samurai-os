Arch Linux, sharpened

Samurai OS Plain Arch with a keen edge.

A personal Arch-based distribution. Arch's own packages, untouched, with a thin signed layer on top: an installer that encrypts by default, updates that run through pacman and take a snapshot first, and a rescue path you can walk from the USB stick.

The steel is Arch's. We only fold the edge, oil the blade, and keep a spare in the sheath.

The way

A thin layer on plain Arch

Upstream does most of the work. Samurai OS configures what Arch and its neighbours already ship, and packages only the few things that are its own.

What it is

Arch underneath, ours on top

  • Arch's repositories, unchanged. Kernels, Mesa, NVIDIA and KDE come straight from Arch mirrors.
  • The CachyOS repository for linux-cachyos and its prebuilt NVIDIA modules, placed after Arch's repos, so it can add packages but never replace Arch's.
  • Chaotic-AUR the same way, below Arch (ADR-0007): prebuilt AUR packages, with signature checking and a pinned key.
  • One signed repository of our own, [samurai], built and signed on the maintainer's machine and served from GitHub Releases with SigLevel = Required DatabaseRequired. It holds only our tools, configs and meta-packages.
  • pacman is the updater. samurai update wraps one pacman -Syu that takes Arch packages and ours in the same transaction.

What it is not

No forks, no second path

  • Not a custom kernel. Not a fork or rebuild of Arch packages, and no package ever shadows an Arch one.
  • Not a second package manager, a store or a separate GitHub downloader: partial upgrades are how Arch systems break, so everything goes through pacman.
  • Not an image-based or immutable OS. A classic mutable Arch system, with snapshots.
  • Not for BIOS machines. x86_64 UEFI only.
  • Not finished, and not yet tested on real hardware.

The blade today

What already works

Every item here is exercised by a scenario in the QEMU/KVM test suite before it counts as done. Spec'd but unbuilt work lives in the Roadmap.

  • Installer

    VM-tested

    Encrypted btrfs by default

    LUKS2 full-root encryption, on unless you say no. Inside it, btrfs with a flat subvolume layout: @, @home, @cache, @log, @snapshots and more, so rolling back the system never rolls back your files or logs. A 2 GiB FAT32 ESP is mounted at /boot. Every install also gets CPU microcode in the initramfs, zram swap (half of RAM, up to 8 GiB, zstd) and time sync with systemd-timesyncd.

  • Installer

    VM-tested

    Guided, or from a profile

    A graphical installer on the live desktop, or samurai-install in a terminal, asks for disk, hostname, timezone, encryption, kernels, bootloader, desktop, software, user and shell, then writes one validated install-profile.toml. Feed that file back with --profile to install the next machine the same way. A copy stays at /var/lib/samurai/install-profile.toml.

  • Desktop

    VM-tested

    KDE Plasma by default

    Plasma with SDDM, Konsole, Dolphin, Kate, Ark, Gwenview and Okular, Breeze Dark as the default theme with a two-panel layout and monitor widgets. GNOME, Xfce, LXQt or no desktop can be picked in the installer, but only KDE is tested.

  • Boot

    VM-tested

    Two kernels, two sources

    linux-cachyos from CachyOS boots by default, linux-zen from Arch sits beside it: one bad upstream release cannot take out both. linux, linux-lts and linux-cachyos-lts are options. Bootloader: Limine by default or GRUB, both tested; systemd-boot and rEFInd are selectable but not yet VM-tested.

  • Installer

    VM-tested

    Offline install

    The offline ISO carries a local pacman repository with the whole default package set: KDE Plasma, both kernels and the driver stacks. The installer resolves against that repository, so a machine gets only what its profile and hardware need. The test points the package mirror at an address that does not exist, installs anyway, reboots and checks the result, including both kernel and initramfs pairs in /boot.

  • Hardware

    VM: packages only

    GPU driver stacks

    Mesa with Vulkan for AMD and Intel (plus Intel VA-API) and Nouveau Vulkan, always. The NVIDIA open modules go on only when an NVIDIA GPU is detected (or forced in the profile): prebuilt when every chosen kernel has a package, DKMS otherwise. The VM suite builds the DKMS modules for both default kernels; no physical GPU has been tested yet.

  • Desktop

    VM-tested

    Samurai Toolbox

    A KDE app over the samurai command: health and repairs, apps, cleanup, kernels and boot settings, updates, snapshots and diagnostics. Anything that changes the system asks for the administrator password.

  • Software

    VM: installed

    Ready on first boot

    Command-line tools, fonts, KDE apps, Docker and a gaming set (Steam, Heroic, GameMode, MangoHud, gamescope, GE-Proton, Proton-CachyOS, Wine) by default, each a choice in the installer. Optional: browsers, Python 3.10-3.13, Miniforge, AI command-line tools, Ollama, Tailscale and a reverse proxy. No game has been launched in testing yet.

  • Updates

    VM-tested

    Staged updates and a notifier

    samurai update runs preflight checks, refreshes mirrors, shows Arch news and stops on unhandled manual-intervention items, runs scripted fixes (interventions), takes a snapshot, then one pacman -Syu, then checks DKMS, initramfs and boot entries. The notifier, a systemd user timer, counts updates with checkupdates and never installs anything itself. pacman-contrib's weekly paccache timer keeps the package cache to the last few versions.

  • Recovery

    VM-tested

    Snapshots and rescue rollback

    snapper with snap-pac takes a pre/post pair around every pacman transaction. samurai rescue runs from the live ISO: mount, chroot, reinstall bootloader, rebuild initramfs, reinstall kernels, roll back. The test breaks the initramfs, boots the ISO, rolls back and boots the restored system.

  • Process

    34 tests

    Proven in a VM first

    A headless QEMU/KVM + OVMF harness drives the ISO over serial and the guest agent: ISO boot, default install, guided install, KDE, offline install, rollback, update from an Arch archive snapshot, and an update with an intervention.

One command, a few subcommands

The samurai CLI is written in Rust: health checks with fixes, diagnostics with a redacted support bundle, cleanup, mirror refresh and kernel management, next to updates, snapshots, apps and rescue.

$ samurai help
usage: samurai <command> [args]

  update    staged system update
  apps      optional apps from the catalog
  snap      snapshot manager
  rescue    recovery tool
  status    last update check and report
  health    health checks, with fixes
  diag      diagnostics and a redacted support bundle
  clean     free disk space (preview first)
  fix       repair pacman lock, keyring, DKMS
  mirrors   show or refresh the mirrorlist
  boot      boot entries, timeout, kernel options
  kernel    list, install, remove, set default

Download

Two installers, both x86_64 UEFI. Both are on the latest GitHub release, next to a SHA256SUMS file and its signature. Releases are tagged v<major.minor.patch.build>, for example v0.0.1.75; the ISO file names carry the build date.

Offline ISO

About 7.7 GB, shipped in four parts.

  • Installs with no network at all; run samurai update afterwards.

Get the offline parts

Join the offline parts

Download every …offline-x86_64.iso.0* part and SHA256SUMS into one folder. The shell sorts the parts in order.

cat samurai-os-*-offline-x86_64.iso.0* > samurai-os-offline-x86_64.iso

Verify before you trust

Check what you downloaded against the release's checksums. --ignore-missing skips files listed there that you did not download.

sha256sum -c --ignore-missing SHA256SUMS

A signed release also carries SHA256SUMS.sig, made with the Samurai build key. Import the public key shipped in the samurai-keyring package (primary fingerprint DFE8 C148 C042 AA3C 199A AEA0 8436 E127 31ED D3FA) and check the signature before the sums.

gpg --import build-key.txt
gpg --verify SHA256SUMS.sig SHA256SUMS

Draw the blade

Install guide

Requirements: an x86_64 machine booting in UEFI mode, at least 4 GiB of RAM, and a disk you are willing to erase (the guided install wipes the whole disk you pick).

  1. Download and verify

    Take the online or offline ISO from the Download section, join the offline parts if you chose that one, and run sha256sum -c.

  2. Write it to a USB stick

    Samurai OS is built with archiso, so the ISO is a hybrid image: write it raw to the stick, not as a file. This erases the stick. Find its name with lsblk first.

    $ sudo dd if=samurai-os-offline-x86_64.iso of=/dev/sdX bs=4M status=progress oflag=sync

    Replace /dev/sdX with the stick, never a partition like /dev/sdX1 and never your system disk. Ventoy usually boots archiso images, but it has not been tested with Samurai OS yet.

  3. Boot the stick in UEFI mode

    Turn Secure Boot off for the live ISO, as with Arch's own. The live system starts a Plasma desktop. Ethernet connects by itself; for Wi-Fi use the network applet.

  4. Run the installer

    Open Install Samurai OS (graphical) on the desktop. It lists the disks, walks through the choices, shows a summary and starts only after you confirm the erase. The disk passphrase is never written to the profile. Prefer a terminal? The second icon runs the same install as questions:

    # samurai-install

  5. Or reinstall from a saved profile

    Reuse an install-profile.toml from a previous install for an identical machine. The profile is validated against a strict allowlist before any disk is touched.

    # samurai-install --profile my.toml --disk /dev/nvme0n1 --yes

  6. Reboot and keep it sharp

    Unlock the disk, log in to Plasma, and update whenever you like with samurai update. If a boot ever goes dark, boot the stick again and use samurai rescue.

The armoury

Optional apps, at install or any time later

samurai apps reads one catalog: Garuda's setup-wizard list, imported as data, plus our own additions. Pick apps in the install profile or any time afterwards; every package is checked against the enabled repositories before anything runs, so you never get halfway into a transaction that cannot finish.

One transaction, no partial upgrades

Installs are a single pacman -S --needed, shown before it runs. The tool never syncs databases on its own: if they are stale it sends you to samurai update first. Bundles skip what is not available yet and say why.

Bundles: @gaming, @dev, @creative, @office, @media, @streaming.

The armour

Security

The goal is secure by default without breaking games, Steam or Proton. Part of the baseline is built; the rest is specified and scheduled.

Built

today

In every install

  • LUKS2 full-root encryption on by default; /boot is the unencrypted ESP.
  • Signed [samurai] repository and database (SigLevel = Required DatabaseRequired); Arch's signing used as is.
  • Root account locked; your user is in wheel.
  • Install profiles are checked against a strict allowlist: no free-form shell, every value quoted, passwords only as crypt hashes.
  • firewalld on by default: zone public, inbound closed except DHCPv6; SSH opens only when you enable the SSH server. The guided wizard asks (default yes); profiles set [security] firewall.
  • No SSH server unless you ask for one.
  • Packages and release checksums are signed with a dedicated subkey on the maintainer's machine.

Specified

roadmap · M8

Coming next

  • One-click firewall presets for KDE Connect, Steam, Sunshine and more.
  • Secure Boot with your own keys (sbctl, Microsoft keys kept for option ROMs) and Limine's config checksum enrolled.
  • Optional TPM2 unlock with a PIN by default, plus a one-time recovery key.
  • Kernel and sysctl hardening; AppArmor at boot; unprivileged user namespaces kept for Flatpak, Steam and browser sandboxes.
  • Tailscale in its own firewall zone, so joining a tailnet exposes nothing by itself.
  • An opt-in paranoid profile and samurai security status.

Questions at the gate

FAQ

Should I put this on my main machine?

Not yet. Samurai OS is early and built for one owner first. Everything listed as working passes a VM test, but no physical-hardware test has been run. A VM or a spare machine is the right place.

What licence is it under? Can I use it at work?

Our code is under the PolyForm Noncommercial License 1.0.0: free for personal use, hobby projects, study, research, and use by schools, charities and government bodies. It is source-available, not OSI open source. Using it inside a for-profit company, selling it or hosting it for money needs a separate commercial licence: open an issue and ask. The Arch and CachyOS packages it installs keep their own licences. Details: LICENSING.md.

Why not just use Arch, CachyOS or Garuda?

The aim is to feel like Garuda (a toolbox that fixes things, snapshots before risky changes, guided updates) and run like CachyOS (hardware detection, performance defaults) while staying as close to plain Arch as possible, so upstream does most of the work. If you are happy with any of those, stay there.

Where do updates come from?

From Arch's mirrors and CachyOS's repository for upstream packages, and from the signed [samurai] repository on GitHub Releases for our own. All of it in one pacman -Syu, wrapped by samurai update. Nothing else downloads or installs packages.

What if an update breaks the system?

Every pacman transaction gets a snapshot before and after. If the system no longer boots, boot the USB stick and run samurai rescue rollback. A second kernel from a different repository is also always in the boot menu.

Why is the offline ISO split into parts?

GitHub release files are limited to 2 GiB each, and the offline image with KDE, two kernels and the driver stacks is larger than that. Join the parts with cat and check them with sha256sum (see Download).

Does it support BIOS or Secure Boot?

BIOS/MBR boot is not supported: x86_64 UEFI only. The live ISO boots with Secure Boot off, like Arch's. Secure Boot with your own keys after install is on the roadmap.

What about NVIDIA?

When an NVIDIA GPU is present, the installer adds NVIDIA's open kernel modules: the prebuilt package when every kernel you picked has one (linux-cachyos, linux, linux-lts), otherwise DKMS for all of them, because the module packages conflict with each other. NVIDIA's open modules cover Turing (RTX 20 / GTX 16) and newer; older cards get Nouveau. CUDA and other GPU extras come with a later milestone.

Is there a graphical installer?

Yes. The ISO boots into a Plasma desktop with icons for the graphical installer, the terminal installer and rescue. Both installers write the same install profile and run the same engine. Today they erase the whole disk: no dual boot or manual partitioning yet.

Can I remove the Samurai layer later?

That is the design rule: remove our packages and you should still have a working Arch system. Our defaults ship as packages that drop files into vendor directories, and your own changes in /etc and your home are never overwritten silently.
